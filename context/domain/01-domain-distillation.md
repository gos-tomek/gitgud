# GitGud — Domain Distillation

## STEP 0 — Project Context

### Vision

> "Mentoring, code review quality, and unblocking work — the contributions that keep engineering teams healthy — are invisible to the tools that measure engineering performance."
> — prd.md:20

GitGud classifies code review comments by **semantic intent** (mentoring, architecture, bug-catch, nitpick, unblocking, question) and presents each engineer's Contribution Profile — to themselves and to their Supervisor — without rankings or comparisons.

### Stack & Business Logic Layers

- **Framework**: Astro 6 SSR + React 19 + Tailwind 4 + shadcn/ui on Cloudflare Workers
- **Database**: Supabase (PostgreSQL + RLS + pgcrypto)
- **AI**: Cloudflare Workers AI (Llama 3.3 70B) with majority-vote (3 repeats)
- **Business logic layers**:
  - `src/lib/services/` — services (boards, classification, github-sync, impact-metrics, homepage-stats)
  - `src/pages/api/` — API routes (Zod validation, authorization, delegation to services)
  - `src/worker.ts` — Cloudflare Workflow (sync + classification orchestration)
  - `supabase/migrations/` — schema, RPCs, RLS policies (access logic)
  - `src/types.ts` — entity and DTO types
- **No dedicated domain layer**: business logic is spread across services, SQL RPCs, and API routes. There is no domain module in the DDD sense.

### Recommendation #1 for refactoring: **Thread Aggregate**

**Why**: Thread is the most valuable entity in the system — it carries the semantic classification, which is the product wedge. Today there is no formal Thread entity; its construction is procedural (scattered across `classification.ts:assembleThreadPayload`, `impact-metrics.ts:computeThreadMetrics`, `impact-metrics.ts:getThreadMessages`). Each of these functions independently decides what a "thread" is (root comment + replies via `in_reply_to_id`).

Extracting a Thread aggregate would:

1. Establish a **single source of truth** for thread definition (root + replies + classification + vote).
2. Move invariants (non-bot, valid intent/domain, majority-vote) from procedural code into the entity.
3. Make the classification domain (Core) explicit and testable in isolation from Supabase/Workers AI.
4. Prepare the ground for future work: classification correction, history tracking, re-classification after Vote.

## Summary

This document contains: **24 domain concepts** with source quotes from PRD/roadmap and code locations; **6 subdomains** classified as Core (2) / Supporting (2) / Generic (2); **4 aggregate candidates** with 14 invariants and an assessment of their enforcement; **8 model-vs-code divergences** (one critical — comment content retention violates a PRD guardrail); **4 refactoring priorities**.

**Key finding**: GitGud has a clear core domain (semantic classification + contribution profile), but its central entity — **Thread** — is not explicitly modeled as an aggregate. It is scattered across services, RPCs, and DTO types. Extracting a Thread aggregate is the highest-value refactoring: it establishes a responsibility boundary around the product wedge and makes classification invariants declarative rather than procedural.
