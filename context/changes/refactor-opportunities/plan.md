# Refactor opportunities — Implementation Plan

## Overview

Ship the top-3 refactor opportunities identified in `research.md` (C1 cross-boundary Workflow-dispatch contract, C2 row-shape type bridge, C9 typed API-route helpers) as three strictly sequential phases on branch `change/refactor-opportunities`. Phase 1 also folds in the two verified-trivial housekeeping items (C3 dedupe `SupabaseClient` aliases, C5 delete `createGitHubClient`). Two hermetic tests are added as safety nets: one closes the zero-coverage authz gate at `sync/status.ts:53` (Phase 1), one enforces the C9 route-URL contract at CI (Phase 3).

## Current State Analysis

Grounded in `research.md` (verified at commit `683b9f2` via ast-grep):

- **C1 — dispatch contract lives across three files as string literals.** `ClassificationBatchParams` is defined in `src/worker.ts:22-40`; the only typed edge to `sync.ts` / `sync/status.ts` is the generic on `src/env.d.ts:13`. Readers re-declare their own snake_case row types: `impact-metrics.ts` has 5 (`PrDb:27`, `ReviewDb:44`, `CommentDb:52`, `ClassifiedThreadRow:965`, `ThreadMessageRow:1120`), `classification.ts` has 2 (`CommentRow:32`, `PrRow:43`), `boards.ts` has 2 (`ContributorInput:4`, `BoardRow:12`). - **C4 — dual env-var declaration (`env.d.ts` + `astro.config.mjs env.schema`).** Verdict: intentional constraint (two runtimes need separate typings). The recommended fix is a small tooling addition (`scripts/check-env-schema.ts`), not a code refactor. Out of scope; open a separate change if it becomes friction.
- **C6 — GitHub error-class catch surface.** Fix has two halves: (a) code-only symmetric catches + Sentry classification and (b) user-facing signal decision. Half (b) is a product decision (research §10.1). Deferred until that decision lands.
- **C7 — `AbortSignal` plumbing.** Rejected — tried in `324241c` and ripped out in `070e781` because `step.sleep` invalidates plugin-set signals. Cannot proceed without new Cloudflare-side knowledge on `WorkflowStep` cancellation (research §8).
- **C8 — non-transactional per-batch writes in `syncPrBatch`.** Explicitly stopped — target shape depends on unanswered business decision on partial-iteration semantics (research §10.5).
- **New lint tooling beyond the two hermetic tests.** No `knip` / `ts-prune`, no dep-cruiser URL rule. Both were on the safety-net menu and were deliberately declined during planning; open a follow-up change if the hermetic tests prove insufficient.
- **Migrating tests-side `SupabaseClient` aliases** as a separate concern. Phase 1 also fixes the 4 test-side aliases (`tests/hermetic/sync-pr-batch.test.ts:6`, `classification-voting.test.ts:5`, `sync-review-comments.test.ts:6`, `list-and-upsert-prs.test.ts:6`) because they're one grep-and-replace away — but they don't get their own subsection.
- **Restructuring `src/types.ts`.** Only the four unused camelCase GitHub mirrors are deleted. Everything else in that file stays.

## Implementation Approach

Three phases, one branch (`change/refactor-opportunities`), strict sequence. Each phase is one PR against `main` following the repo's workflow rule ("`main` only advances via merged PR"). Each phase is independently reversible.

**Sequencing rationale (research §5 ranking):**

- Phase 1 first because C1 is the highest-leverage item (pipeline hotspot #1) and its scope is small (one new leaf module + 3 call-site edits) — bundling C3 + C5 in the same PR is cheap because the same services already need re-touching.
- Phase 2 second because C2's blast radius overlaps mostly with services already touched in Phase 1 — landing Phase 1 first makes Phase 2's diffs cleaner. Also, C2 sets up shared row types that Phase 3's follow-ups (e.g. typed response bodies) could later build on.
- Phase 3 last because C9 is UI-side and doesn't touch pipeline services at all — it composes cleanly on top of the earlier two.

**Ownership inversion (Phase 1 correction from planning discussion):** `workflow-contract.ts` is the source of truth for `ClassificationBatchParams`. `worker.ts` consumes it; `env.d.ts:13` references it. If `workflow-contract.ts` only re-exported from `worker.ts`, nothing would structurally change — this is called out here so the implementer picks the right direction.

## Critical Implementation Details

- **Phase 1 — ownership direction.** `workflow-contract.ts` must **define** `ClassificationBatchParams`; `worker.ts` and `env.d.ts` become consumers. Re-exporting the type from `worker.ts` leaves `worker.ts` as the source of truth and is a no-op structurally.
- **Phase 2 — diff-check placement.** `supabase gen types typescript --local` requires a running Supabase instance. The only CI job with one is `test-integration` in `.github/workflows/ci.yml` (has `npx supabase start`). The regeneration + `git diff --exit-code` step goes there — placing it in `validate` will fail with no Supabase to talk to. The same is true for the pre-commit hook: do not add generated-types regeneration to `lefthook.yml`; local Supabase may not be running during commit.
- **Phase 2 — Row type scope.** Only pipeline tables need re-exported Row aliases in `src/db/rows.ts`. Do not re-export every table — keep the surface minimal to make future column additions explicit consumers of the shared type.
- **Phase 3 — helper module placement.** `src/lib/api-routes.ts` is on the client side. Do not import it inside `src/pages/api/**` route handlers themselves — they own their own URL by virtue of the file path; the module exists to give **callers** a typed handle on where to `fetch`.

## Phase 1: C1 workflow-contract + C3 SupabaseClient dedupe + C5 delete dead export

### Overview

Extract the cross-boundary Workflow-dispatch contract into a single owned module. Fold in the two housekeeping items so this PR clears the noise at the top of the tree before Phase 2 touches the same services.

### Commit sequence (enforce landing order)

The `Changes Required` items below are listed by concern, not by commit. Land them in this order so the hermetic characterization test proves semantic equivalence **before** any call site is touched:

- **Commit 1a — characterization first.** New module (§1) + hermetic test (§6). Test includes the equivalence table (see §6 contract): for a set of instance-ID inputs, assert `parseBoardInstanceId(id)?.boardId !== boardId` returns the same boolean as `!id.startsWith(\`board-${boardId}-\`)`. Lands green with the module unused.
- **Commit 1b — migrate consumers.** `worker.ts` (§2) + `env.d.ts` (§3) + `sync.ts` (§4) + `sync/status.ts` (§5). The characterization test continues to pass, proving the new call sites preserve the pre-refactor authz semantics byte-for-byte.
- **Commit 1c — housekeeping.** C3 `SupabaseClient` dedupe (§7 + §8 + §9) + C5 delete dead export (§10 + §11). Independent of C1; can also be a separate PR at implementer's discretion if the phase-1 review load is too high.

> Item numbers below are listing labels for cross-reference (`§6`, `§10`, etc.); the commit-landing order is defined by the block above.

#### 1. New: workflow-contract module

**File**: `src/lib/workflow-contract.ts`

**Intent**: Own the cross-file Workflow-dispatch contract in one module — the params interface, the instance-ID builder, and the authz-prefix parser. Today these live as string literals + one generic type edge spread across four files.

**Contract**: Exports three symbols:

- `interface ClassificationBatchParams` — moved verbatim from `worker.ts:22-40` (12 fields, all optional except `boardId`).
- `buildBoardInstanceId(boardId: string, dateStamp: string): string` — returns `` `board-${boardId}-${dateStamp}` ``.
- `parseBoardInstanceId(instanceId: string): { boardId: string; dateStamp: string } | null` — inverse of the builder. Implementation: match against `/^board-(.+)-(\d{4}-\d{2}-\d{2})$/`; capture group 1 is `boardId`, group 2 is `dateStamp`; return `null` on no match. Anchoring to the fixed-format dateStamp suffix makes the parse unambiguous even when `boardId` contains hyphens (e.g. UUIDs).

#### 2. worker.ts — consume the shared type

**File**: `src/worker.ts`

**Intent**: Delete the local `ClassificationBatchParams` declaration; import from the new module. Replace the string-literal instance-ID at `worker.ts:514` with a call to `buildBoardInstanceId`. All 10 child `.create()` sites keep their string prefixes for now — those are internal to `worker.ts` and not part of the cross-file contract.

**Contract**: `import type { ClassificationBatchParams } from "@/lib/workflow-contract"`; `import { buildBoardInstanceId } from "@/lib/workflow-contract"`. The 3-line comment at `worker.ts:19-21` about the single-interface constraint moves with the interface.

#### 3. env.d.ts — re-point the generic

**File**: `src/env.d.ts`

**Contract**: `CLASSIFICATION_BATCH: Workflow<import("@/lib/workflow-contract").ClassificationBatchParams>;` replaces the current `import("./worker")` path.

#### 4. sync.ts — use the builder

**File**: `src/pages/api/github/sync.ts`

**Intent**: Replace the open-coded instance-ID string at `sync.ts:59` with `buildBoardInstanceId(boardId, dateStamp)`.

**Contract**: `import { buildBoardInstanceId } from "@/lib/workflow-contract"`; call site takes the existing `boardId` and `dateStamp` locals.

#### 5. sync/status.ts — use the parser as the authz gate

**File**: `src/pages/api/github/sync/status.ts`

#### 6. New hermetic test: workflow-contract round-trip + authz characterization

**File**: `tests/hermetic/workflow-contract.test.ts`

**Intent**: First-ever coverage on the authz gate — and, critically, a **characterization test** that pins the current `sync/status.ts:53` behavior before any call site is touched. If `parseBoardInstanceId` has subtly different semantics than `!instanceId.startsWith(\`board-${boardId}-\`)` (empty strings, unusual dateStamps, boundary prefix collisions), this test catches the divergence at Commit 1a — long before Commit 1b touches the actual gate.

**Contract**: Vitest hermetic test file; no network/DB/subprocess; imports only from `@/lib/workflow-contract`. Three test blocks:

- **Round-trip identity.** For a representative set of `(boardId, dateStamp)` pairs, `parseBoardInstanceId(buildBoardInstanceId(b, d))` returns `{ boardId: b, dateStamp: d }`.
- **Rejection of alien prefixes.** `parseBoardInstanceId("classify-xyz")`, `parseBoardInstanceId("orchestrate-abc")`, `parseBoardInstanceId("")`, `parseBoardInstanceId("board-")`, and other malformed inputs return `null`.
- **Equivalence with the legacy predicate.** For a table of `(instanceId, boardId)` inputs, assert `parseBoardInstanceId(instanceId)?.boardId !== boardId` returns the same boolean as `!instanceId.startsWith(\`board-${boardId}-\`)`. Cover at minimum: exact match (`"board-B-2026-08-15"`vs`boardId="B"`), cross-board (`"board-OTHER-2026-08-15"`vs`boardId="B"`), prefix-collision (`"board-B2-2026-08-15"`vs`boardId="B"` — must reject; both predicates must agree), empty string, and non-`board-` prefix. If any row disagrees, the migration is not semantics-preserving and the test fails before any call site changes.

## Phase 2: C2 row-shape type bridge (generated via `supabase gen types`)

### Overview

Introduce generated `Database` types from `supabase gen types typescript --local` as the single source of truth for DB row shapes. Migrate readers first (`impact-metrics.ts`, `classification.ts`, `boards.ts`), then writers (`github-sync.ts`, `worker.ts`), then delete the unused camelCase mirrors. Wire a CI diff-check into `test-integration` so migrations and types can't drift.

### Commit sequence (enforcement before migration)

Land in this order so the CI diff-check is enforcing drift **before** any consumer migrates:

- **Commit 2a — landing pad, no consumers.** `db:types` script (§1) + generated `src/db/database.types.ts` (§2) + `src/db/rows.ts` re-export module (§3). Nothing else changes; the module compiles, no imports touch it yet. Lands green.
- **Commit 2b — enforcement on.** CI diff-check step in `test-integration` (§10). At merge time the committed `database.types.ts` matches `supabase gen types` output, so the check lands green — but any future PR (including the migration commits below) that touches migrations without regenerating will now fail CI.
- **Commit 2c — migrate `impact-metrics.ts` readers** (§4). One file, one commit; hermetic + integration tests pass under CI enforcement.
- **Commit 2d — migrate `classification.ts` readers** (§5).
- **Commit 2e — migrate `boards.ts` readers** (§6).
- **Commit 2f — migrate `github-sync.ts` + `worker.ts` writers** (§7 + §8).
- **Commit 2g — delete unused camelCase mirrors** (§9). Ordered last so the deletion happens only after every migrated consumer has been rebased onto shared row types.

Commits 2c–2g can also be bundled into a single "migrate all consumers" commit if the diffs stay small; the essential ordering constraint is that 2a and 2b land before any migration.

## Phase 3: C9 typed API-route helper module

### Overview

Move every `/api/…` URL literal in `src/components/**` into a single typed helper module. Bootstrap with the two `SyncIndicator.tsx` URLs and the filesystem-scan hermetic test that enforces the contract; then roll to the remaining 10 component files.

### Changes Required:

#### 1. New: api-routes helper module

**File**: `src/lib/api-routes.ts`

**Intent**: Own URL construction for every `/api/…` endpoint the client calls. One helper per endpoint; parametric endpoints take typed arguments.

**Contract**: Exports per-endpoint functions returning URL strings. Signatures (implementer adjusts as the roll-out proceeds — this is the starting set from `SyncIndicator.tsx`):

- `apiGithubSync(): "/api/github/sync"`
- `apiGithubSyncStatus(query: { boardId: string; instanceId?: string }): string`

Add helpers for every URL enumerated in research §9 V27–V30 (`/api/github/*`, `/api/board/*`, `/api/board/{id}/threads/*/vote`, `/api/auth/*`, `/api/impact/*`, `/api/profile/pat`, etc.) as the roll-out reaches each component. Path templates like `` `/api/board/${boardId}/…` `` become `apiBoardThreads(boardId)` etc.

#### 2. Bootstrap: migrate SyncIndicator.tsx

**File**: `src/components/impact/SyncIndicator.tsx`

**Intent**: Replace the two literals at `:46` (status URL with query string) and `:62` (dispatch URL) with helper calls. Establishes the pattern; smallest possible commitment; reversible.

**Contract**: `import { apiGithubSync, apiGithubSyncStatus } from "@/lib/api-routes"`; call sites take the same `boardId` / `instanceId` locals already in scope.

#### 3. New hermetic test: URL contract enforcement

**File**: `tests/hermetic/api-routes.test.ts`

**Intent**: Walk `src/pages/api/**` and assert that every URL returned by an `api-routes.ts` helper resolves to an existing route file. If a route is renamed without updating the helper (the PR #32 failure mode), this test fails at CI.

**Contract**: Test uses an inside-out approach — enumerate route files first, then match helpers against them:

- (a) Walk `src/pages/api/**` using `fs.readdirSync` (Node 22+ / no extra dep) and collect all `.ts` route files. Convert each filepath to a URL pattern by stripping the `src/pages` prefix, stripping the `.ts` extension, converting bracketed segments (`[boardId]`, `[login]`, etc.) to a wildcard regex token, and normalising `index` to the parent path. This builds a set of known URL patterns from ground truth.
- (b) For every exported function in `src/lib/api-routes.ts`, call it with plausible sample arguments (`boardId = "test"`, `instanceId = "test"`, etc.), strip the query string, and assert the resulting path matches at least one pattern from step (a).

This approach avoids guessing which URL segments are dynamic — the route file itself is the source of truth. A renamed route removes its pattern; any helper that matched it now has no match and the test fails.

#### 4. Roll to remaining 10 component files

**Files** (10, in order of URL count):

- `src/components/board/CreateBoardForm.tsx` (7 URLs: validate-pat, repos, collaborators, profile/pat, board/check-name, validate-repo, board)

- `src/components/account/ChangePasswordForm.tsx` (1)

**Intent**: Each file's `fetch("/api/…")` string literals become `fetch(apiXyz(...))`. Any URL parameter interpolation moves into the helper signature. Prefer one commit per component file for reviewability; a single PR bundling all 10 is acceptable if diffs stay small.

**Contract**: Every URL literal moves; the helper module gains one function per endpoint touched. After this step, `git grep -Pn 'fetch\(\s*["'\''\`]/api/' src/components/` must return nothing.
